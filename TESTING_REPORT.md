## Известные ограничения текущей реализации

### 1. Playwright и WB

- **Селекторы могут меняться**: если WB обновит вёрстку, селекторы в `scraper.py` потребуют обновления
- **Капча**: при обнаружении капчи система останавливается с ошибкой (обход не реализован)
- **Rate limiting**: частые запросы могут привести к блокировке IP
- **imtId**: для некоторых товаров может не обнаруживаться автоматически

### 2. База данных

- **SQLite не поддерживает timezone**: сравнение дат публикаций использует UTC
- **Нет миграций**: изменения схемы требуют ручного ALTER TABLE
- **Отсутствует индекс для llm_requests по date**: может замедлиться при большом объёме

### 3. LLM интеграция

- **Парсинг JSON**: LLM может вернуть JSON с маркерами ```json```, обрабатывается базово
- **Нет retry для rate limit**: если LLM API вернёт 429, попытка не повторится
- **Дневной лимит глобальный**: не учитывает успешность запросов

### 4. n8n workflows

- **Упрощённая обработка переделок**: revision-handler предполагает, что переделывается последний ожидающий пост
- **Нет состояния между сообщениями**: контекст "ожидания замечания" не сохраняется строго
- **Обработка ошибок базовая**: нет retry логики в workflows

### 5. Безопасность

- **API не защищён**: endpoints доступны без аутентификации (предполагается закрытая сеть)
- **Секреты в .env**: при компрометации .env все ключи раскрыты
- **Логи могут содержать чувствительные данные**: при отладке

## Рекомендации по тестированию на сервере

### Этап 1: Базовая проверка (1-2 часа)

1. Развернуть систему на сервере
2. Запустить в режиме DRY_RUN=true
3. Добавить тестовый товар 913340343
4. Проверить логи сборщика
5. Проверить, что данные записались в БД
6. Проверить, что анализ выполнился (если LLM доступен)
7. Проверить, что пост создан
8. Проверить работу команд бота

### Этап 2: Полный цикл (2-4 часа)

9. Одобрить тестовый пост
10. Запустить публикацию вручную (вызвать endpoint /publish)
11. Проверить dry-run сообщение
12. Добавить ещё 2-3 реальных товара
13. Протестировать переделку поста
14. Протестировать пропуск товара
15. Проверить расписание публикаций

### Этап 3: Боевой режим (после одобрения)

16. Установить DRY_RUN=false
17. Добавить бота в тестовый канал
18. Опубликовать один пост в тестовый канал
19. Проверить форматирование и отсутствие ссылок
20. Настроить основной канал
21. Включить боевую публикацию

## Тестовые сценарии для проверки

### Сценарий 1: Нормальный поток

```
1. /add 913340343
2. Ждём сбора (смотрим логи)
3. Получаем пост от бота
4. Нажимаем "Одобрить"
5. Ждём времени публикации или вызываем /publish вручную
6. Проверяем публикацию
```

**Ожидаемый результат:** Пост опубликован, статус = published

### Сценарий 2: Переделка

```
1. Получаем пост от бота
2. Нажимаем "Переделать"
3. Пишем: "Добавь больше деталей о размерах"
4. Ждём новой версии
5. Проверяем, что версия увеличилась
6. Одобряем
```

**Ожидаемый результат:** Новая версия поста с учётом замечания

### Сценарий 3: Повторное добавление

```
1. /add 913340343 (уже был добавлен)
2. Проверяем ответ бота
```

**Ожидаемый результат:** Сообщение о том, что товар уже обработан

### Сценарий 4: Некорректный ввод

```
1. /add abc123
2. /add https://example.com
3. /add https://wildberries.com/../../../etc/passwd
```

**Ожидаемый результат:** Ошибка валидации, артикул не добавлен

### Сценарий 5: Проверка лимитов

```
1. Добавить 3 товара
2. Одобрить все 3
3. Опубликовать 2 в один день
4. Попытаться опубликовать 3-й
```

**Ожидаемый результат:** 3-й не публикуется (лимит 2/день)

### Сценарий 6: Перезапуск

```
1. Добавить товар в очередь
2. docker-compose restart
3. Проверить /queue
```

**Ожидаемый результат:** Товар остался в очереди
